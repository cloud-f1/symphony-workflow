## Story 3: Formalize the git-tag release process with scripts/release.sh

**User story:** As the person cutting a symphony-workflow release, I want a single script that bumps both version files, verifies a matching CHANGELOG entry exists, runs the version-sync test, and creates the annotated git tag, so that a release can't silently skip the tagging step the way v0.3.0 and v0.4.0 did (CHANGELOG said 'tagged', `git tag -l` disagreed until this Epic).

**Acceptance criteria:**
- scripts/release.sh <version> bumps pyproject.toml's [project].version and plugin/.claude-plugin/plugin.json's version to <version> together, in one step
- scripts/release.sh fails loudly (non-zero exit, clear message) if CHANGELOG.md has no `## <version>` heading yet, so the changelog entry must be written before the script is run, not after
- scripts/release.sh runs `uv run pytest tests/test_version.py` (the existing version-sync test) and aborts without tagging if it fails
- scripts/release.sh creates an annotated tag (`git tag -a v<version>`) and prints, but does not itself run, the exact `git push`/`git push --tags` commands -- matching this repo's existing confirm-before-pushing posture
- README.md gains a 'Releasing' section documenting scripts/release.sh's usage and the manual push step
- A decision is recorded on whether to retroactively create git tags v0.3.0 and v0.4.0 to match the CHANGELOG's existing 'tagged' claims, or to explicitly leave that historical gap -- not silently dropped either way

**Tasks:**
- **Write scripts/release.sh** — Implement the version bump for both pyproject.toml and plugin/.claude-plugin/plugin.json, the CHANGELOG.md heading check, the tests/test_version.py run, and annotated-tag creation ending in a printed (non-executed) push command, per spec.md section 5's design.
- **Add a 'Releasing' section to README.md** — Document scripts/release.sh's usage (arguments, prerequisites -- CHANGELOG entry written first -- and the manual git push step) in README.md.
- **Record the retroactive-tag decision** — Decide (recording the decision, e.g. in the Story or a follow-up comment) whether to retroactively `git tag` v0.3.0/v0.4.0 to match CHANGELOG.md's existing claims, and act on it if yes.
- **Dry-run the script end-to-end before calling it done** — Manually exercise scripts/release.sh against a throwaway version bump (not a real release) to confirm each of its steps -- version bump, CHANGELOG check, test run, tag creation, printed push command -- actually works, since scripts/ has no existing automated test pattern to reuse for shell scripts.

## Story 4: Consolidate the duplicated Jira-only-backend guard into tracker.py

**User story:** As a developer adding a new tracker-agnostic-vs-Jira-only call site, I want one shared function in tracker.py that decides whether a client supports Jira-only operations, so that cli.py and api.py can't independently drift into two different error messages or behaviors for what is supposed to be the same decision.

**Acceptance criteria:**
- tracker.py gains a single function (e.g. `require_jira(client, *, context: str) -> JiraClient`) used by both cli.py's Jira-only commands and api.py's get_jira_client(), each passing its own `context` string for the error message
- cli.py's `_jira_client()` (currently constructs a fresh JiraClient from JiraConfig.from_env() directly) and api.py's `get_jira_client()` (currently does isinstance(client, JiraClient) against the already-selected app.state.tracker_client and raises HTTPException 501) are migrated onto the shared function without changing either's externally observed behavior -- same typer.Exit(code=1) in the CLI, same 501 in the API
- Existing test_cli.py and test_api.py coverage of the Jira-only paths (search/call/decompose/sync-decomposition; /tools, /tools/{name}/call) still passes -- error message wording may be unified, but exit codes/status codes are unchanged
- A new test in test_tracker.py covers require_jira() directly: given a JiraClient it returns it unchanged; given a LinearClient it raises with the passed context reflected in the message

**Tasks:**
- **Confirm the actual shape of both existing guards before designing the shared function** — Re-read cli.py's `_jira_client()` and api.py's `get_jira_client()` side by side -- they are not identical today (cli.py builds a fresh JiraClient from env rather than type-checking an already-selected tracker client the way api.py does) -- so require_jira()'s signature needs to accommodate both call shapes, not assume they're the same check written twice.
- **Implement require_jira() in tracker.py** — Add the consolidated function per the confirmed shape from the investigation above, with a `context` parameter so each caller can describe what needs Jira without duplicating the check.
- **Migrate cli.py and api.py to call require_jira()** — Replace cli.py's Jira-only-command guard and api.py's get_jira_client()'s isinstance check with calls to tracker.require_jira(), removing the duplicated logic from both files.
- **Update/add tests covering the consolidated behavior** — Add a direct test for require_jira() in test_tracker.py, and adjust test_cli.py/test_api.py as needed so they still assert the same exit codes/status codes after the migration.
